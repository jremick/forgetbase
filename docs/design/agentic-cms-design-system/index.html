Design system package

Quiet Control Plane with a Governed Reading Room

A business-grade UI system for Agentic CMS: dense operational chrome for maintainers and admins, with a first-class fallback reading experience for typical users. The system treats trust metadata, permissions, versioning, and provenance as primary interface content.

Self-contained HTML First release reader path React/Vite ready

Primary product read

Instruction control plane, not a human CMS

Agentic CMS manages governed instruction assets for agents, APIs, CLIs, MCP clients, SDKs, and AI harnesses. The web UI is the operational surface for browsing, approval, debugging, and fallback reading.

The first release must make the reader path polished enough for normal consumers: browse approved guidance, read comfortably, verify trust, copy a stable ID, and understand whether a document is in scope.

Design language: restrained, accessible, high-density, provenance-forward. No marketing landing page, decorative gradients, one-note palette, or card-heavy SaaS layout.

Resolved Design Decisions

Grounded in current repo docs and schema
Sensitivity taxonomy

Use the current schema exactly: public-demo, internal, restricted, confidential, and secret. The open-source demo corpus should use public-demo only. Anonymous public access requires all three: sensitivity=public-demo, lifecycle=active, and status=approved.

Asset cardinality

The UI should model one governed asset as a stable identity with versioned content. Current create/update payloads accept one instruction object and/or one human document per update, while detail/export surfaces return arrays. Design for zero-to-many instruction objects and zero-to-many human documents per asset, with first-release views optimized for the common one-plus-one case.

No-access disclosure

Do not reveal sensitive metadata to unauthorized users by default. Direct hits should use a generic restricted/unavailable state unless policy says the title/owner can be shown. Admins can see hidden counts and denial evidence; readers only get sign-in or access-request guidance.

Reader write scope

First-release readers are read/search/query consumers. They can copy stable IDs and content snippets. Managed-query feedback can exist for authenticated users where supported, but annotations, comments, and suggested edits are later work.

Dark theme

Light theme ships first. Tokens reserve a dark-theme path, but dark mode is not a first-release requirement because fallback reading quality and admin density matter more.

Tenant visibility

Single-tenant OSS is the first target, with tenant_id in the model. Show the current tenant in admin/system context and connection settings, but do not add a tenant switcher to reader chrome.

Authoring scope

No rich web authoring for first release. Content is imported or managed through API/CLI/MCP/admin flows. The UI supports reading, review, publish, restore, version inspection, raw/rendered toggles, and operational forms.

Hierarchy rules

Top levelUse the three product groups: Read, Work, and Operate. They are stable navigation landmarks, not user-created folders.
FoldersFolders sit under a group and collect related governed pages or assets, such as Guardrails, Templates, Review queue, Providers, or Policies.
Sub-pagesSub-pages are leaf destinations under folders. They can be human pages, asset detail pages, saved operational views, or generated lists.
Active leafThe current page uses aria-current="page", a left keyline, selected tint, and stronger text weight.
Active ancestorExpanded parent folders use a quieter tint and border so users can see the current path without confusing it with the selected page.
Expanded/collapsedExpandable groups and folders expose aria-expanded. Collapsed rows retain counts and due markers so hidden work remains visible.
Resizable widthThe desktop page tree has a draggable right-edge separator with a 240-420 px range. Store the user width in browser storage and restore it on reload.

Use folders when

The user needs persistent orientation across related pages, nested assets, or operational categories. Folders should be permission-aware and count only visible items unless admin disclosure mode is active.

Use tabs when

The user is already inside one stable object and switches between sibling views, such as human document, agent instruction, versions, audit, and raw JSON.

Use filters when

The information is the same list narrowed by metadata, such as status, sensitivity, owner, surface, review date, source, or permission state.

Use breadcrumbs when

The page can be reached from several paths or deep links. Breadcrumbs show location and parent return points; they do not replace the main tree.

State and marker rules

CountsUse compact numeric pills for visible child count, due count, or hidden admin count. Label the count in accessible text in implementation.
SensitivityShow sensitivity with the existing marker component. Do not use sensitivity color alone as the item state.
PermissionsNo-access rows are muted, labelled, and non-interactive unless the policy allows request-access action.
Review dueDue work can appear on folder and leaf rows. A folder badge summarizes children; the leaf badge names the exact state.

Accessibility guidance

StructureUse role="tree" and role="treeitem" only when implementing full tree keyboard behavior; otherwise use a nested navigation list.
KeyboardSupport Up and Down to move rows, Right to expand or enter, Left to collapse or move to parent, Home and End to jump.
Current pageApply aria-current="page" to one active leaf. Do not put current-page state on parent folders.
Non-color signalPair color with labels, keylines, icons, text weight, and visible badges for selected, due, restricted, and denied states.
MobileCollapse the tree behind a navigation button or drawer. Preserve breadcrumbs and selected-page title in the top bar after the drawer closes.

Implementation guidance

Incremental Build Path

1

Tokens

Replace ad-hoc CSS with custom properties, shared status/sensitivity styles, focus rules, density variables, and shadcn/ReUI semantic tokens.

2

Foundation

Adopt local shadcn-style primitives for buttons, badges, commands, and status states before installing richer registry components.

3

Shell

Add role-aware app shell, grouped nav, command/search bar, and connection/session drawer.

4

Reader

Build Library, Search, Asset Read, TrustBanner, metadata rail, sources, and instruction well.

5

Workflows

Migrate review queue, publish, restore, version compare, and asset audit into template pages.

6

Operations

Use ReUI selectively for data grids, filters, frames, trees, timelines, and steppers when an operational workflow needs richer console behavior.

Component source order: local governed-asset primitives first, shadcn core for foundational controls, ReUI only for richer app-console components, and custom components only when permission, sensitivity, export, or audit behavior requires it.
Acceptance bar: reader can find and trust an approved public-demo asset without admin concepts; maintainer can review and publish with audit clarity; admin can manage keys/providers/policies without exposing raw secrets except one-time create/rotate reveal.
